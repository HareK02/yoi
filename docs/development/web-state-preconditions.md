# Web state checks and retained identities

The Web client uses purpose-specific content and operation identities, not an independent update counter. The checks below describe current boundaries, not a claim that the full cleanup or final generated-contract validation is complete.

| Boundary                       | What is compared, how, and when                                                                                                                                                                                                                                                                                                                               | Why order or time alone is insufficient                                                                                                                                                                                                                         |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Config source commit           | The editor sends its saved `base_digest` and staged changes; update/rename/delete carry each observed entry's `expected_digest`. Local WASM checks entry conditions before replacing local content. The Server owns persistence admission. Success installs the returned snapshot as the new base; rejection retains the draft until explicit reload/reapply. | A later request can be authored from old content. Digests identify the actual source tree/entry, including a return to identical content; wall-clock age is not the condition.                                                                                  |
| Config diagnostics             | Before publication the editor requires a non-aborted request and filters diagnostics by the analyzed tree digest.                                                                                                                                                                                                                                             | A late result is not evidence about currently displayed source. Content identity and asynchronous invalidation are different checks.                                                                                                                            |
| Drive update/relocate/delete   | The controller pins `expectedMutationId` from the user's observed node. The adapter sends it unchanged. `workspace-drive::mutate` checks current `last_mutation_id` via `changeable` in the same SQLite transaction before mutation. Publication stores the actual successful request ID and a durable receipt.                                               | This identifies a real mutation, not a separately allocated state number. Content-only equality misses move/rename or ABA return to identical bytes. Last-arriving writes can overwrite another operation's result; timestamps do not prove operation identity. |
| Drive read/preview             | Each chunk checks the current node's `last_mutation_id` against the observed operation inside the store transaction. Conflict does not silently switch to latest bytes.                                                                                                                                                                                       | Chunks from different writes must not be combined, regardless of arrival order.                                                                                                                                                                                 |
| Drive response-loss recovery   | Before sending, the controller records one pending request ID. Pending/unknown receipts block another write for that selection. Recovery queries the same request. The store checks actor and typed payload against the existing receipt fingerprint before returning its result.                                                                             | Unknown outcome does not mean the write failed. A fresh ID can duplicate a committed side effect; ordering cannot identify which payload committed.                                                                                                             |
| UI asynchronous publication    | Selection and write/page invalidation fences are checked before publishing returned data. These are local request-lifetime fences, not persisted resource-state conditions.                                                                                                                                                                                   | The projection follows the latest selected request, not the last response to arrive. No server-visible opaque state number is needed here.                                                                                                                      |
| Subject behavior save          | The client sends exact `expected_behavior_md`, including empty text, with the replacement. A successful response must describe the requested text; mismatch is an unknown outcome and is not automatically retried.                                                                                                                                           | Observed text already supplies the content condition; no extra counter is needed. Application to Worker history is a separate operation.                                                                                                                        |
| Memory history display         | `change_id` and `current_change_id` identify immutable entries. The parser preserves Server order; current/historical is exact identity equality.                                                                                                                                                                                                             | Stable links need immutable identities, but IDs do not establish chronology and must not be parsed or sorted as numbers.                                                                                                                                        |
| Runtime trust display          | The parser requires verification `binding_id` to equal the displayed binding. Mutations use the observed enrollment identity; revoke confirmation also compares the exact displayed key fingerprint before sending.                                                                                                                                           | Re-enrolling the same public key creates a different binding lifetime. Matching key bytes or a recent response cannot make old verification current.                                                                                                            |
| Merge Request review freshness | Review/request `subject_ref` must match current Git source ref. Revoked verdicts are excluded; effective events follow supplied thread order. Merged results use validated immutable integration evidence, not a new live observation.                                                                                                                        | Source equality identifies what was reviewed. Arrival order or target-only movement cannot confer approval on another source commit.                                                                                                                            |

`ConfigProjectionValidator` is a typed static-template-catalog validation policy (`kind`, namespace, key aliases), not an opaque freshness token. Source tree, projection and toolchain digests describe different inputs/results. Key fingerprints identify key bytes; binding IDs identify enrollment lifetimes; mutation IDs identify actual committed requests. These are not interchangeable and are not increasing numbers.

WIP remains `0.2.0`; naming cleanup alone does not justify a new package/protocol version or generic validator number. Final API/OpenAPI/protocol freshness must be checked after authoritative Rust changes are integrated. Earlier Web build or test success does not prove that final generation check.

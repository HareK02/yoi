## Implemented boundaries

- `job`: neutral immutable request/limits/result envelope, fingerprint, strict
  registry selectors, bounded digests and read-only intent/attempt/outcome DTOs.
  No HTTP, Workspace, Runtime identity, domain grants, runner or workflow DSL.
- Backend reuses validation/result helpers and neutral projections while retaining
  its exact request wire/fingerprint/envelope, domain grants, persistent states,
  Runtime authorization, unknown fences, resource serialization and cleanup.
- `worker::job`: selected registry Profile/instruction/model, explicit requirement
  rejection, bounded policy, distinct ephemeral Internal Worker, result-only
  FeatureModule and Host-fenced structured acceptance. No parent filesystem,
  Workspace, Feature or domain connections; no Profile-name authorization.
  Ambiguous sink acceptance is Unknown unless the Host's durable result proves success.
- Standalone Host owns schema-1 SQLite intent/attempt/result/ack state and a bounded
  execution service. It opens and recovers under its Worker lease; shutdown cancels
  and awaits executions, closes SQLite, then releases the lease after controller
  confirmation. Old cloned handles are closed. Drop cannot attest cleanup and
  retains the lease. Busy/unknown/cancelled/terminal work is not blindly replayed.
- Exact immutable request resend differs from explicit bounded new-attempt retry.
  Results commit before resource release, survive model/notification failure, and
  are independently acknowledged by the consumer. Waiting does not relinquish
  Host ownership of cancellation/concurrency. Cancelling unknown intent retains
  its uncertain attempt evidence and serialization fence.
- Optional `builtin:job` is a caller-selected compatible policy, not a fixed runner
  default. Different user registry Profiles are demonstrated in Worker fixtures.
  Existing `builtin:backend-job` retains Backend behavior; standalone rejects its
  unavailable requirements rather than silently stripping or replacing them.
- No production Server/Runtime process, HTTP/WS listener, Worker registry,
  subprocess Worker, daemon/pool or subjektiv-specific runner is added.

### Actual process verification versus fixtures

`process_loss_recovers_durable_jobs_without_replaying_unknown` starts **only a
test-owned copy of the integration test executable**, using scripted model clients.
The child owns a real StandaloneHost/SQLite connection/Worker lease, persists a
reserved request, a cancelled request and an accepted result, then exits with code
23 while a separate Internal Worker is executing. It deliberately skips destructors
and graceful shutdown. The parent verifies that exit and restores the Host through
the real stale-process lease path: accepted result retained/unacknowledged,
cancelled work never resumed, reserved work explicitly resumable and interrupted
work Unknown/no automatic retry. The helper's ignored annotation is an entry-point
selector, not skipped semantic coverage.

These are real Rust test/compiler processes plus scripted in-process model
executions and SQLite fixtures. They are **not** live-provider LLM calls, a live
standalone CLI/TUI session, a Backend/Runtime deployment or dogfood environment
update. No operating Yoi Worker or live dogfood process was stopped or updated.
Production Jobs do not create the subprocess used solely by that crash test.
